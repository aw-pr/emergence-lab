## 19:43-20:03Z — twenty minutes of nothing, two causes stacked

The queue sat at five pending with no agent running. Neither cause was visible

and the batch handoff landed. Twenty minutes of dispatch lost to a version

**Cause 2, revealed by fixing cause 1: the reserve config had become a dispatch
window.** The tick then logged:

```
schedule stop worker 82 (claude): clock 21:01 is outside the 01:00-06:00
dispatch window; it next opens at 01:00; no new dispatch this tick
```

`window_reserve.overnight.start`/`end` does double duty in
`quota_schedule_permits_dispatch`: it sets the reserve percentage *and*
declares a hard window outside which no new worker dispatch happens at all.
Arming the operator's "80% cap from 01:00" as an overnight block had therefore
silently confined the entire run to 01:00-06:00 — the exact opposite of the
instruction, which was to leave 22:00-01:00 uncapped.

There is no way to express "uncapped tonight, capped from 01:00" in that block.
Remedy: the overnight block is deleted, leaving top-level `percent: 0, action:
hold` so tonight runs uncapped; and a one-shot LaunchAgent
(`com.autometta.arm-reserve-0100`) sets the top-level `percent: 20` at 01:00,
which arms the reserve without declaring a window. Verified after the change
that dispatch resolves as permitted at 21:05, 23:30 and 02:30.

Worth a card in autometta: one key controlling two unrelated behaviours, where
setting it for the second silently disables the first.
